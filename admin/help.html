Website editing guide

The public website is a static GitHub Pages site. Pages CMS is the normal editing interface and saves approved content directly into the website repository. This guide covers routine editing, member portfolios, events, payments, the Design Studio community showcase, publishing, troubleshooting, and future chapter handoff.

Article 01

Getting started with the editor

Use Pages CMS for routine website updates. Editors should not need to edit JSON, HTML, CSS, or JavaScript directly.

  1. Open Pages CMS and sign in with an account authorized for the chapter website repository.
  2. Select the repository containing the AIAS Memphis website.
  3. Use Website for Site settings, Chapter members, Support & payments, and Custom pages.
  4. Use Chapter content for Events, Student projects, and Jobs & internships.
  5. Use Community for approved Design Studio showcase entries.
  6. Make the change and save it.
  7. Open the affected public page and verify the result after GitHub Pages republishes the site.
Use GitHub only when necessary. GitHub is primarily for repository ownership, permissions, deployment history, code changes, and recovery. Normal content editing belongs in Pages CMS.

Article 02

Use the Admin Dashboard and Site Health checks

The Admin Dashboard is the first place to look before a presentation, major event, semester transition, or launch. It summarizes content and checks common publishing mistakes.

  • Review invalid public emails and external links.
  • Replace prototype/sample content.
  • Check event dates and RSVP URLs.
  • Resolve duplicate or invalid project, member, event, and custom-page identifiers.
  • Fix projects missing covers, galleries, image descriptions, or narratives.
  • Fix project-to-member links that reference nonexistent profiles.
  • Clean up expired jobs still marked active.
  • Review incomplete public member profiles.
  • Review Community Showcase entries before publication.
A warning is not always a broken website. Site Health deliberately flags incomplete or placeholder content. Fix errors first, then decide whether advisory warnings are acceptable.

Article 03

Edit site settings, contact information, and social links

Open Website → Site settings. These values are reused across multiple pages.

  • Full chapter name — chapter identification and footer.
  • Header name — shorter navigation name.
  • Tagline — short supporting phrase.
  • Homepage headline/introduction — primary homepage copy.
  • Chapter description — main About-page description.
  • Public contact email — chapter-wide contact and Design Studio submission destination when it is a real address.
  • Instagram URL — reused on the homepage, About page, and footer.
  • AIAS membership URL — destination for Join AIAS buttons.
  • UofM Architecture URL — department link.
  • Announcement banner — optional message above navigation.
Before launch: replace placeholder contact information, add the real Instagram URL, and remove prototype/sample messaging.

Article 04

Create and maintain chapter member profiles

Open Website → Chapter members. This directory is for the chapter membership broadly, not only formal officers.

  1. Create a permanent Member URL name, such as jordan-smith.
  2. Add the public name and chapter role/contribution.
  3. Optionally add program/year and design or professional interests.
  4. Upload a profile photo and useful photo description. Initials appear automatically when no photo is supplied.
  5. Write the short introduction/blurb.
  6. Optionally add a richer full profile description.
  7. Add a public email only with permission.
  8. Keep Show public member profile enabled only when the person should appear publicly.

The About page previews members; the Members page contains the searchable directory, quick-view popouts, and links to full profiles with linked student projects.

Public profile consent matters. Confirm the member approves publication of their name, photo, bio, email, interests, and school work.

Article 05

Link student projects to member profiles

Projects and member profiles are connected using the member's stable URL name.

  1. Open Website → Chapter members and copy the person's Member URL name.
  2. Open Chapter content → Student projects.
  3. Paste the exact value into Member profile URL name.
  4. Save the project.
  5. Open the member profile and confirm the project appears.
  6. Open the project page and confirm the profile link appears correctly.
Do not guess the slug. Copy it from the member entry. The Admin Dashboard flags projects that reference an unknown member URL name.

Article 06

Publish and maintain a student project portfolio

  1. Open Chapter content → Student projects.
  2. Enter project title, student name, and a permanent Project URL name.
  3. Optionally link the project to a chapter member.
  4. Add studio/course, semester, year, and project type when useful.
  5. Write a concise short summary and choose a strong cover image.
  6. Build the project gallery in presentation order. Each item needs an image and accessibility description; captions are optional.
  7. Write the full project description using rich text.
  8. Optionally add an external portfolio/publication/video URL.
  9. Use Feature on homepage when appropriate.
  10. Save and test the card, full detail page, gallery controls, and member association.
Publishing permission: confirm the student permits public use of their name and work. Do not publish grades, private critiques, confidential client material, or firm work without authorization.

Article 07

Publish an event and control RSVP behavior

  1. Open Chapter content → Events.
  2. Create a permanent Event URL name.
  3. Add date, time, location, short summary, optional image, and image description.
  4. Use Full event details for agenda, speakers, parking, what to bring, participating firms, or other expanded information.
  5. Feature important upcoming events on the homepage when appropriate.

RSVP buttons

An RSVP button appears only when Show RSVP button is on and the Registration URL is a valid full https:// link. If either condition fails, the button stays hidden.

Past events

The date automatically determines whether an event appears as upcoming or past. Past events remain available as an archive.

Article 08

Post a job, internship, or opportunity

  1. Open Chapter content → Jobs & internships.
  2. Add title, organization, location, and opportunity type.
  3. Add posted/deadline dates when known.
  4. Write a concise summary rather than copying a complete outside posting.
  5. Add the original employer/source application URL.
  6. Use Show on website to control visibility.

A listing with a valid past deadline automatically stops displaying publicly even if it remains marked active.

Article 09

Manage the Support & Payments page

Open Website → Support & payments. The website does not process or store payment information; it links to approved third-party accounts.

  1. Edit the firm-payment and donation explanatory text.
  2. Add a provider and public button label.
  3. Paste the full approved https:// payment-account URL.
  4. Turn on Show this payment button.
  5. Save and verify the public destination yourself.

If no enabled method has a valid URL, the public page shows a safe “payment links are being updated” state.

Financial safety: never store bank/card credentials, passwords, tokens, private keys, or API secrets. Do not claim donations are tax-deductible unless formally confirmed.

Article 10

Moderate the Design Studio and Community Showcase

The public Design Studio is a browser-based 2D building-composition tool. Visitors can create with simple shapes, recolor/resize/rotate them, choose a background, save a local draft, export a PNG, and generate a share link.

Shareable is not the same as permanently published

A visitor's share link contains the complete design state in the URL. It can be opened or remixed immediately without an account. It does not automatically write anything into the chapter repository or permanent public gallery.

The permanent Community Showcase is intentionally moderated because GitHub Pages has no secure anonymous-write backend.

Approve a submitted design

  1. Receive the visitor's share link/design code. When a real chapter Public contact email is configured, the Design Studio provides a submission email button automatically.
  2. Open the submitted share link and inspect the building.
  3. Confirm the supplied building name and designer name are appropriate for public display.
  4. Confirm the person is comfortable having that designer name published.
  5. Open Community → Community designs in Pages CMS.
  6. Add a new entry with the approved Building name and Designer name.
  7. Paste the Design code exactly as submitted. Do not edit the encoded code by hand.
  8. Turn on Show in community showcase.
  9. Optionally turn on Feature this design to sort it near the beginning.
  10. Save, then open Design Studio → Community Showcase and click View / remix to verify it reconstructs correctly.

Hide or remove a design

Turn off Show in community showcase to hide an entry without losing it. Delete the entry only when leadership intentionally wants it removed from the curated list.

Why the design code is stored

The showcase stores the portable design code rather than the current test-site URL. If the repository or domain is transferred later, the website reconstructs a new local share link automatically.

Moderate before publishing. Do not publish abusive/inappropriate titles, impersonation, personal information, or a person's name without their approval. The design tool is intentionally limited to simple geometric content, but the public attribution fields still require review.

Article 11

Create a custom information page

  1. Open Website → Custom pages.
  2. Add a clear title and permanent lowercase Page URL name.
  3. Optionally provide a shorter navigation label.
  4. Enable Show in main navigation only for pages that deserve a permanent top-level link.
  5. Add an introduction, optional hero image/description, and formatted content.
  6. Save and test the public page.

Article 12

Images, uploads, and accessibility descriptions

Images uploaded through Pages CMS are stored under assets/uploads/ and move with the repository during ownership transfer.

  • Use JPG, PNG, or WebP for normal photos, drawings, and renderings.
  • Compress unnecessarily large files before uploading.
  • Use portrait-oriented photos for member profiles and landscape covers for many event/project cards.
  • Write concise descriptions for meaningful images.
  • Use captions when a drawing/model/diagram benefits from explanation.
  • Do not upload work the chapter lacks permission to publish.

Article 13

Links, rich text, and permanent URL names

External links

Use complete URLs beginning with https:// for RSVP forms, jobs, social accounts, payment accounts, portfolios, and other outside destinations.

Rich text

Full project descriptions, event details, custom-page content, and member descriptions support headings, paragraphs, lists, emphasis, links, and supported images.

URL names / slugs

Member, project, event, and custom-page URL names use lowercase letters, numbers, and hyphens. Treat them as permanent after publication.

Article 14

Publishing, verification, and change history

Saving in Pages CMS writes content to GitHub as a commit. GitHub Pages then republishes the static website.

  1. Confirm the CMS save completed.
  2. Refresh the affected public page.
  3. Check important edits at desktop and phone widths.
  4. Click newly added external links.
  5. For events, test the detail page and RSVP visibility.
  6. For projects, click through the gallery and member association.
  7. For members, test the directory/popout and full profile.
  8. For payments, verify each destination.
  9. For a community design, open its showcase card and confirm View / remix reconstructs the submitted design.

Git history retains previous repository states so administrators can investigate or recover content.

Article 15

Manage editor access and collaborators

Only people responsible for maintaining the chapter website should have editing access.

  • Authorized GitHub users can edit through Pages CMS after the app is authorized for the repository.
  • CMS collaborators are separate from public chapter-member profiles.
  • Add replacement editors before removing outgoing people.
  • Revoke access that is no longer needed.
  • Keep at least two current people capable of administering long-term ownership.
  • Never share one GitHub password among the chapter.

Article 16

Transfer the website to future chapter leadership

The website should be transferred, not rebuilt. The repository contains the site, CMS schema, JSON content, uploaded media, community-design codes, and Git history.

  1. Create/confirm the chapter-controlled GitHub organization or durable owner.
  2. Add at least two current administrators.
  3. Transfer the existing repository.
  4. Verify GitHub Pages still publishes from the correct branch/root.
  5. Authorize Pages CMS under the new repository owner.
  6. Verify every CMS section loads, including Community designs.
  7. Re-invite CMS-only collaborators if needed.
  8. Verify the public URL/custom domain.
  9. Test at least one stored Design Studio showcase code after transfer.
  10. Remove the previous owner/test-account access only after the handoff is confirmed.
No content rebuild is required. Portable design codes also survive a repository/domain transfer because the site generates current local remix links at runtime.

Article 17

Troubleshooting common problems

A saved CMS change is not visible

Confirm the save completed, refresh the public page, and check GitHub Pages deployment status if necessary.

A member or linked project is missing

Verify public-profile visibility and confirm the project's Member profile URL name exactly matches the member's Member URL name.

An RSVP/payment button is missing

Check its visibility toggle and ensure the required URL is a complete valid https:// address.

A job disappeared

Check its deadline and Show on website toggle. Expired jobs automatically stop displaying.

A Design Studio share link says invalid

Ask the visitor to create a fresh share link/code from the Design Studio. Do not manually repair or shorten the encoded code.

A showcase card is missing

Confirm the entry exists under Community → Community designs, has a valid Design code, and Show in community showcase is enabled.

The submission button is missing

The Design Studio only shows its email submission button when Site settings contains a valid non-placeholder Public contact email. Visitors can still create/copy a share link and design code.

A local Design Studio draft disappeared

Draft saving uses that visitor's browser storage. Clearing browser/site data or switching devices/browsers can remove access to the local draft. Share links and PNG exports are better for portable copies.

Pages CMS shows a React/configuration error

Hard-refresh Pages CMS first. If the problem continues, have a site administrator inspect .pages.yml rather than experimenting with raw YAML.

Article 18

Privacy, permissions, moderation, and content safety

The repository is public. Treat everything entered through Pages CMS as information that may be publicly accessible even if it is not currently rendered.

  • Never store passwords, API keys, tokens, recovery codes, banking credentials, or card information.
  • Never publish grades, student records, private critiques, or other protected educational data.
  • Get permission before publishing a member's portrait, biography, email, project work, or a Design Studio creator's name.
  • Use chapter-wide contact information when practical.
  • Do not publish copyrighted photography, firm/client work, or third-party material without permission.
  • Moderate Community Showcase titles and designer attribution before publication.
  • Verify payment, RSVP, job, portfolio, social, and other external links.
When uncertain, leave it out and confirm first. Removing sensitive content later does not guarantee it was never copied, cached, shared, or retained in repository history.
