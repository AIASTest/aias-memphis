Website editing guide

The public website is a static GitHub Pages site. Pages CMS is the normal editing interface and saves content directly into the website repository. This guide covers routine editing, publishing, member portfolios, payments, troubleshooting, and future chapter handoff.

Article 01

Getting started with the editor

Use Pages CMS for routine website updates. Editors should not need to edit JSON, HTML, CSS, or JavaScript directly.

  1. Open Pages CMS and sign in with an account authorized for the chapter website repository.
  2. Select the repository containing the AIAS Memphis website.
  3. Use Website for Site settings, Chapter members, Support & payments, and Custom pages.
  4. Use Chapter content for Events, Student projects, and Jobs & internships.
  5. Make the change and save it.
  6. Open the affected public page and verify the result after GitHub Pages republishes the site.
Use GitHub only when necessary. GitHub is primarily for repository ownership, permissions, deployment history, code changes, and recovery. Normal content editing belongs in Pages CMS.

Article 02

Use the Admin Dashboard and Site Health checks

The Admin Dashboard is the first place to look before a presentation, major event, semester transition, or launch. It summarizes website content and automatically checks for common publishing mistakes.

What Site Health checks

  • Invalid public email addresses and external links.
  • Prototype/sample content that still needs replacement.
  • Missing or invalid event dates and RSVP URLs.
  • Duplicate or invalid project, member, and custom-page URL names.
  • Projects with missing covers, galleries, accessibility descriptions, or narratives.
  • Projects linked to member profiles that do not exist.
  • Expired job listings that are still marked active.
  • Public member profiles missing recommended profile information.
A warning is not always a broken website. Site Health intentionally flags incomplete or placeholder content so leadership can review it. Fix errors first, then decide whether lower-priority warnings are acceptable.

Article 03

Edit site settings, contact information, and social links

Open Website → Site settings. These values are reused across multiple pages, so update them here rather than trying to edit each page separately.

  • Full chapter name — used for chapter identification and footer content.
  • Header name — shorter name used in the navigation.
  • Tagline — short supporting phrase.
  • Homepage headline/introduction — primary homepage copy.
  • Chapter description — main About-page description.
  • Public contact email — chapter-wide contact when available.
  • Instagram URL — reused on the homepage, About page, and footer.
  • AIAS membership URL — destination for Join AIAS buttons.
  • UofM Architecture URL — department link.
  • Announcement banner — optional message above the main navigation.

Announcement banner

Clear the field completely to hide the banner. Keep announcements short enough to work well on phones.

Before launch: replace placeholder contact information, add the real Instagram URL, and remove prototype/sample messaging.

Article 04

Create and maintain chapter member profiles

Open Website → Chapter members. This directory is for the chapter membership broadly, not only formal officers. A person's role can describe any public contribution to AIAS.

  1. Create a permanent Member URL name, such as jordan-smith.
  2. Add the member's public name and Chapter role / contribution.
  3. Optionally add program/year and design or professional interests.
  4. Upload a profile photo and add a useful photo description. If no photo is supplied, the website displays initials.
  5. Write the Short introduction / blurb for directory cards and quick-view content.
  6. Optionally add a richer Full profile description for the member's expanded profile.
  7. Add a public email only with the member's approval.
  8. Keep Show public member profile enabled only when the person should appear publicly.

What visitors see

The About page previews chapter members. The Members page provides the full searchable directory. Selecting a member opens a quick-view popout, and the full member profile shows the person's profile information plus their linked student projects.

Member URL names

Treat the member URL name as permanent once published. It is used by profile links and project associations. Changing it later can break saved links and disconnect projects until those projects are updated.

Public profile consent matters. Confirm the member approves publication of their name, photo, bio, email, interests, and school work.

Article 05

Link student projects to member profiles

Projects and member profiles are connected using the member's stable URL name. Do not maintain a separate project list inside a member profile.

  1. Open Website → Chapter members and copy the person's Member URL name.
  2. Open Chapter content → Student projects.
  3. Edit the project and paste that exact value into Member profile URL name.
  4. Save the project.
  5. Open the member's full profile and confirm the project appears.
  6. Open the project detail page and confirm the member/profile relationship appears correctly.

Example

If a member's URL name is jordan-smith, the project field must also be exactly jordan-smith.

Older-content fallback: older projects without an explicit member link may still match a member when the Student name corresponds to that member's name. The explicit Member profile URL name is more reliable and should be used for new projects.
Do not guess the slug. Copy it from the member entry. The Admin Dashboard flags projects that reference an unknown member URL name.

Article 06

Publish and maintain a student project portfolio

Each student project has a reusable dedicated detail page. Leadership does not create a separate HTML file for every project.

  1. Open Chapter content → Student projects and add or edit an item.
  2. Enter the project title, student name, and permanent Project URL name.
  3. Optionally link the project to a chapter member using Member profile URL name.
  4. Add studio/course, semester, year, and project type when useful.
  5. Write a concise Short project summary for cards and the project hero.
  6. Choose a strong Cover image and write a cover-image description.
  7. Build the Project gallery in presentation order. Each gallery item needs an image and accessibility description; captions are optional.
  8. Write the Full project description using the rich-text editor.
  9. Optionally add a full https:// external portfolio, publication, or video link.
  10. Use Feature on homepage for work that should be highlighted.
  11. Save, then test the card, full project page, gallery controls, and member-profile association if used.

Gallery behavior

Visitors can use the large image, previous/next buttons, thumbnails, or keyboard arrow keys. Gallery order in the CMS controls presentation order.

Project URL names

A project URL name should normally never change after the project has been shared. Changing it changes the public project link.

Publishing permission: confirm the student permits public use of their name and work. Do not publish grades, private critiques, confidential client material, or firm work without authorization.

Article 07

Publish an event and control RSVP behavior

Event cards open dedicated event-detail pages. Use the short summary for cards and the Full event details field for the expanded page.

  1. Open Chapter content → Events.
  2. Create a permanent Event URL name.
  3. Add the date, time, location, short summary, optional image, and image description.
  4. Use Full event details for agenda, speakers, parking, transportation, what to bring, participating firms, or other detailed information.
  5. Turn on Feature on homepage for important upcoming events.

RSVP buttons

An RSVP button appears only when both conditions are true:

  • Show RSVP button is turned on.
  • Registration URL contains a valid full https:// link.

If the toggle is off, the RSVP button stays hidden even when an old URL is still saved. If the toggle is on but the URL is blank or invalid, the button also remains hidden.

Past events

The date automatically determines whether an event appears as upcoming or past. Past events remain available as an archive unless leadership intentionally removes them.

Do not repurpose an old event slug for an unrelated event. Add a new event entry instead so previously shared links remain meaningful.

Article 08

Post a job, internship, or opportunity

  1. Open Chapter content → Jobs & internships.
  2. Add position title, organization/firm, location, and opportunity type.
  3. Add posted and application-deadline dates when known.
  4. Write a concise summary rather than copying an entire outside job posting.
  5. Add the employer's original full https:// application link.
  6. Use Show on website to publish or hide the listing immediately.

If a valid deadline exists, the public website automatically stops displaying the listing after that date. Site Health still flags an expired listing that remains marked active so it can be cleaned up.

Verify before publishing. Link to the original employer/source when possible and confirm that the opportunity is still legitimate and current.

Article 09

Manage the Support & Payments page

Open Website → Support & payments. The website does not process or store payment information. It only directs firms, partners, donors, and supporters to approved third-party chapter payment accounts.

Page sections

  • Firm payment section — explanation for firms paying career-fair, sponsorship, or other chapter-related charges.
  • Donation section — general support/donation language.
  • Payment buttons — links to PayPal, Venmo, Cash App, Zelle, or another approved provider.
  • Memo, receipt, and donation notes — optional clarification for payment identification or receipt questions.
  • Payment contact email — optional payment-specific contact; the site can fall back to the main chapter email.

Publish a payment button

  1. Add the payment provider.
  2. Add the public button label.
  3. Paste the full approved https:// account/payment URL.
  4. Turn on Show this payment button.
  5. Save and click the public button yourself to verify the destination.

If no enabled payment method has a valid URL, the public page shows a safe “payment links are being updated” message instead of a broken or placeholder button.

Financial safety: publish links only to chapter-approved accounts. Never store card numbers, bank credentials, passwords, recovery codes, tokens, private keys, or API secrets in the website repository. Do not claim donations are tax-deductible unless that status has been formally confirmed.

Article 10

Create a custom information page

Custom pages are useful for resources, scholarships, competitions, committees, travel information, professional-development material, or other chapter-specific content that does not need a dedicated website feature.

  1. Open Website → Custom pages.
  2. Add a clear page title.
  3. Create a permanent lowercase Page URL name.
  4. Optionally provide a shorter navigation label.
  5. Turn Show in main navigation on only when the page deserves a permanent top-level link.
  6. Add a page introduction, optional hero image and image description, and formatted page content.
  7. Save and test the public page.
Avoid casually changing a URL name after launch. Existing bookmarks and shared links depend on that slug.

Article 11

Images, uploads, and accessibility descriptions

Images uploaded through Pages CMS are stored inside the repository under assets/uploads/. This means uploaded media moves with the website when ownership is transferred.

Recommended image practice

  • Use JPG, PNG, or WebP for normal photos, renderings, drawings, and diagrams.
  • Compress unnecessarily large image files before uploading.
  • Use a clear portrait or headshot for member profiles.
  • Landscape images usually work best for event/project cover cards.
  • Project gallery images may use different proportions because the detail viewer contains them without forcing one crop.
  • Write concise image descriptions for meaningful visual content.
  • Use visible captions when the drawing, model, diagram, or process image benefits from explanation.

Alternative text

Describe what is important about the image rather than writing “image of.” For architecture work, identify the view or drawing type and the important content, such as “Section drawing showing stepped public terraces and shade structures along the river edge.”

Permission still applies. Do not upload copyrighted images, firm work, client material, or another student's work unless the chapter has permission to publish it.

Article 12

Links, rich text, and permanent URL names

External links

Use the complete URL beginning with https://. This applies to RSVP forms, job applications, social accounts, payment accounts, portfolios, publications, and other external destinations.

Rich-text fields

Full project descriptions, event details, custom-page content, and full member-profile descriptions support formatted text. Use headings to break up long content, lists when appropriate, and links only when they add useful context.

URL names / slugs

Member, project, event, and custom-page URL names use lowercase letters, numbers, and hyphens. Treat them as permanent identifiers after publication. Display titles and names can change without changing the slug.

Why this matters: the site intentionally rejects or hides malformed external links rather than sending visitors to questionable destinations. Site Health also checks common URL mistakes.

Article 13

Publishing, verification, and change history

Saving in Pages CMS writes the edited content to GitHub as a commit. GitHub Pages then republishes the static website.

Verification checklist after a save

  1. Confirm the CMS save completed.
  2. Refresh the affected public page.
  3. Check important content at desktop and phone widths.
  4. Click any newly added external link.
  5. For an event, open the detail page and check RSVP visibility.
  6. For a project, click through every gallery image.
  7. For a member, test the directory/popout and full member page.
  8. If a project was linked to a member, verify the relationship in both directions.
  9. For payment buttons, verify the destination before directing anyone to pay.

History and recovery

Each CMS save becomes part of Git history. If content is accidentally changed or removed, a repository administrator can inspect earlier commits and recover the previous version. Do not try to fix a structural problem by randomly editing raw JSON.

Article 14

Manage editor access and collaborators

Only people responsible for maintaining the chapter website should have editing access.

GitHub-backed editors

Authorized GitHub users with access to the repository can use Pages CMS after the Pages CMS GitHub App is authorized for that repository.

Pages CMS collaborators

Pages CMS can also support invited collaborators for content/media editing. Those invitations are separate from the public member directory; being a public AIAS member does not automatically grant website editing access.

When responsibilities change

  • Add replacement editors before removing outgoing people.
  • Revoke access that is no longer needed.
  • Keep at least two current people capable of administering long-term repository ownership.
  • Never share one GitHub password among the whole chapter.

Article 15

Transfer the website to future chapter leadership

The website should be transferred, not rebuilt. The repository already contains the site code, CMS configuration, JSON content, uploaded media, and Git history.

Preferred long-term ownership

Use a chapter-controlled GitHub organization with at least two current organization owners. Individual editors can use their own GitHub accounts instead of sharing a chapter password.

Repository handoff checklist

  1. Create or confirm the chapter-owned GitHub organization/account that will own the repository.
  2. Add at least two current chapter administrators.
  3. Transfer the existing repository to the chapter-controlled owner.
  4. Verify GitHub Pages is still publishing from the correct branch/root.
  5. Authorize/install Pages CMS for the repository under its new owner.
  6. Open Pages CMS and verify every content section still loads.
  7. Re-invite any CMS-only collaborators if required after ownership changes.
  8. Verify the public website URL/custom domain.
  9. Remove access belonging only to the previous owner/test account after the handoff is confirmed.
No content migration should be required. The member profiles, projects, events, jobs, payment settings, images, custom pages, and CMS schema all remain in the repository during a normal transfer.

Article 16

Troubleshooting common problems

A saved change is not visible

Confirm the CMS save completed, then refresh the public page. If the change still does not appear, check the repository's GitHub Pages deployment status.

A member does not appear in the directory

Confirm the member has a valid Member URL name and Show public member profile is enabled.

A project is missing from a member profile

Compare the project's Member profile URL name with the member's Member URL name. They must match exactly. Check Site Health for an unknown-member warning.

A project/member/event link opens “not found”

The slug in the URL may have been changed or removed. Check the corresponding CMS entry and avoid changing established URL names.

An RSVP button does not appear

Confirm Show RSVP button is enabled and the Registration URL is a complete valid https:// link.

A payment button does not appear

Confirm the payment entry is enabled and has a valid full https:// URL. If no valid methods are enabled, the public page intentionally shows the “links are being updated” message.

A job disappeared

Check the listing deadline and Show on website toggle. Jobs automatically stop displaying after a valid past deadline.

Pages CMS shows a React/configuration error

Hard-refresh Pages CMS first. If the problem continues, do not experiment with raw YAML. Have a site administrator inspect .pages.yml and the affected field definitions.

An uploaded image looks wrong

Confirm the correct image was selected, then check its dimensions and file size. Member photos are portrait-oriented, while project/event covers usually work better as landscapes.

Article 17

Privacy, permissions, and content safety

The website repository is public. Treat everything entered through the CMS as information that may be publicly accessible even if it is not currently rendered on a visible page.

  • Never store passwords, API keys, authentication tokens, recovery codes, banking credentials, card information, or other secrets.
  • Never publish grades, student records, private critiques, schedules containing sensitive information, or other protected educational data.
  • Get permission before publishing a member's portrait, biography, email address, interests, or project work.
  • Use chapter-wide contact information when practical instead of personal addresses.
  • Do not publish copyrighted photography, firm/client work, drawings, or third-party material without permission.
  • Verify payment, RSVP, job, portfolio, social, and other external links before publication.
  • Do not state that donations are tax-deductible unless the chapter's status has been formally confirmed.
When uncertain, leave it out and confirm first. Removing sensitive information after publication does not guarantee it was never copied, cached, or retained in repository history.
