Website editing guide

The main website remains a static GitHub Pages site. Pages CMS handles normal chapter content. The Design Studio can optionally connect to a small Supabase community backend so students can publish designs themselves while the existing curated CMS showcase remains available.

Article 01

Getting started with the editor

Use Pages CMS for normal content updates. Editors should not need to edit JSON, HTML, CSS, or JavaScript directly.

  1. Sign in to Pages CMS with an account authorized for the chapter website repository.
  2. Select the chapter website repository.
  3. Use Website for Site settings, Chapter members, Support & payments, and Custom pages.
  4. Use Chapter content for Events, Student projects, and Jobs & internships.
  5. Use Community for the chapter-curated Design Studio showcase.
  6. Save the change and verify the affected public page after GitHub Pages republishes.
GitHub is not the routine editor. Use GitHub for ownership, permissions, deployment history, code/configuration work, and recovery.

Article 02

Use the Admin Dashboard and Site Health checks

The Admin Dashboard is the first place to look before a presentation, semester transition, or launch.

  • Resolve invalid public emails and external links.
  • Replace prototype/sample content.
  • Check event dates and RSVP URLs.
  • Resolve duplicate/invalid member, project, event, and custom-page identifiers.
  • Fix missing project galleries, descriptions, or accessibility text.
  • Fix project-to-member links that reference nonexistent profiles.
  • Clean up expired jobs.
  • Review incomplete public member profiles.
  • Review curated Community Showcase entries and design-code warnings.
  • Check whether Live Community is Disabled, Auto publish, or Moderated and resolve any backend configuration warning.
A warning is not always a broken website. Site Health intentionally flags placeholders and incomplete content.

Article 03

Edit site settings, contact information, and social links

Open Website → Site settings. These values are reused throughout the public site.

  • Full chapter name — chapter identification and footer.
  • Header name — shorter navigation name.
  • Tagline — short supporting phrase.
  • Homepage headline/introduction — primary homepage copy.
  • Chapter description — main About-page description.
  • Public contact email — chapter-wide contact and fallback Design Studio submission destination.
  • Instagram URL — reused on homepage, About, and footer.
  • AIAS membership URL and UofM Architecture URL — global destinations.
  • Announcement banner — optional message above navigation.
Before launch: replace placeholder contact information, add the real Instagram URL, and remove prototype/sample messaging.

Article 04

Create and maintain chapter member profiles

Open Website → Chapter members. This directory is for chapter membership broadly, not only formal officers.

  1. Create a permanent Member URL name such as jordan-smith.
  2. Add public name, chapter role/contribution, and optional program/year/interests.
  3. Upload a profile photo and useful photo description. Initials are used when no photo is supplied.
  4. Write the short introduction and optional full profile description.
  5. Add a public email only with permission.
  6. Enable Show public member profile only when the person should appear publicly.

The About page previews members; the Members page provides search, popouts, and full profiles with linked projects.

Article 05

Link student projects to member profiles

  1. Open Website → Chapter members and copy the person's Member URL name.
  2. Open Chapter content → Student projects.
  3. Paste it exactly into Member profile URL name.
  4. Save, then verify both the member profile and project page.
Do not guess the slug. Site Health flags project links that point to an unknown member.

Article 06

Publish and maintain student projects

  1. Enter project title, student name, and permanent Project URL name.
  2. Optionally link the project to a chapter member.
  3. Add studio/course, semester, year, and project type.
  4. Write a concise summary and choose a strong cover image.
  5. Build the gallery in presentation order with image descriptions.
  6. Write the full rich-text project narrative.
  7. Optionally add an external portfolio/publication/video URL and homepage feature toggle.
  8. Test the card, detail page, gallery controls, and member association.

Article 07

Publish an event and control RSVP behavior

  1. Create a permanent Event URL name.
  2. Add date, time, location, short summary, optional image, and image description.
  3. Use Full event details for agenda, speakers, parking, or other expanded information.
  4. Feature important upcoming events when appropriate.

An RSVP button appears only when Show RSVP button is enabled and Registration URL is a valid full https:// URL. Past events remain available as an archive.

Article 08

Post a job, internship, or opportunity

  1. Add title, organization, location, and opportunity type.
  2. Add posted/deadline dates when known.
  3. Write a concise summary rather than copying a complete outside posting.
  4. Add the original application URL.
  5. Use Show on website to control visibility.

A listing with a valid past deadline automatically stops displaying publicly even if it remains marked active.

Article 09

Manage Support & Payments

The website does not process money itself; it links to approved third-party payment accounts.

  1. Edit the firm-payment and donation explanatory text.
  2. Add a provider and public button label.
  3. Paste the full approved https:// account URL.
  4. Enable the payment button and verify the public destination.
Financial safety: never store bank/card credentials, passwords, tokens, private keys, or secret API credentials here.

Article 10

Understand the Design Studio game

The Design Studio is a lightweight architecture sandbox designed to be played with, shared, revisited, and remixed.

Core building tools

  • Blocks, roofs, circles, arches, windows, doors, columns, and trees.
  • Direct drag, resize, rotation, colors, materials, opacity, layering, locking, duplicate, Repeat ×3, and Ground.
  • Interactive windows, doors, and trees; night scenes can illuminate window elements.
  • House, Tower, Pavilion, and Courtyard quick starts plus Surprise Building.
  • Undo/redo, snap grid, parts/layers strip, local draft save/load, PNG export, and portable share links.

Play and presentation features

  • Design Roulette combines a random concept, palette, name, and challenge.
  • Build Battle starts a random design plus a three-minute sprint.
  • Today's Brief changes daily to give repeat visitors a new architecture prompt.
  • Night Party switches to a night/neon mood and lights available windows.
  • Mutate Part changes a selected part so students can accept, mutate again, or undo.
  • Desk Crit generates contextual critique prompts and a concept statement from the current composition.
  • Presentation, Focus, X-ray, and Silhouette modes help students read or present the composition differently.
  • Sun Study adds a scrub-able shadow direction for reading massing and depth.
  • My Sketchbook stores up to 12 visual versions on the current device for reopening/remixing without an account.
  • Pin-up poster export creates a 1080×1350 presentation image in addition to the normal PNG.
  • Badges, challenge stamps, optional sound, native sharing on supported devices, and first-visit onboarding reward experimentation.

Two public galleries

Live Community is optional and allows students to self-publish through Supabase when configured. Community Showcase remains the chapter-curated list stored in data/designs.json and edited through Pages CMS.

If the live backend is disabled or unavailable, the Design Studio still works: students can build, use My Sketchbook, save locally, export images, create share/remix links, and submit codes for the curated showcase.

Article 11

Enable Live Community self-publishing

Live Community is deliberately optional. The chapter can keep GitHub Pages + Pages CMS only, or add a small chapter-owned Supabase project so students can publish directly from the browser.

One-time setup

  1. Create a Supabase project owned by the chapter or another durable chapter-controlled account.
  2. Open the Supabase SQL editor and run docs/design-studio-supabase.sql from this repository.
  3. Enable Anonymous Sign-Ins in Supabase Auth settings.
  4. Copy the project's URL and publishable key.
  5. Open data/community-backend.json, paste those two public values, and set enabled to true.
  6. Keep the JSON mode label aligned with the database community_settings.mode. The database—not browser JavaScript—enforces whether new rows become published or pending.
  7. Publish the repository change and test from a private/incognito browser window.
Never paste a secret or service-role key into this repository. Browser code uses a publishable key only. Row Level Security and minimum grants limit what that public client can do.

What students can do in auto mode

  • Publish a building title, public designer credit, optional caption, and design code.
  • Like/unlike live designs.
  • Remix another live design; new posts retain remix lineage.
  • Report inappropriate posts.
  • Remove their own posts while their anonymous browser identity remains available.

Organizer workload

Auto mode requires no approval for ordinary posts. Leadership only needs to review reports or remove inappropriate content in Supabase when necessary. The SQL setup caps one anonymous browser identity at 10 posts per 24 hours.

CAPTCHA is not currently enabled. Do not enable Supabase CAPTCHA protection until the Design Studio client is also updated to provide a CAPTCHA token during anonymous sign-in. Turning it on first would break Live Community sign-in.

Curated showcase still exists

The existing Community → Community designs CMS section remains useful for chapter-picked work, demos, featured designs, or a completely backend-free setup.

Disable Live Community

Set enabled back to false. The live code is not loaded, while the core game and curated showcase continue working.

Article 13

Images, uploads, and accessibility descriptions

Pages CMS uploads are stored under assets/uploads/ and move with the repository during ownership transfer.

  • Use JPG, PNG, or WebP for normal photos, drawings, and renderings.
  • Compress unnecessarily large files.
  • Use portrait-oriented member photos and strong landscape project/event covers.
  • Write concise descriptions for meaningful images and captions when useful.
  • Do not upload work the chapter lacks permission to publish.

Article 14

Links, rich text, and permanent URL names

Use complete https:// URLs for outside destinations. Member, project, event, and custom-page slugs use lowercase letters, numbers, and hyphens and should be treated as permanent after publication.

Article 15

Publishing, verification, and change history

Saving in Pages CMS writes content to GitHub as a commit. GitHub Pages then republishes the static website. Live Community posts are different: they are stored in Supabase and should appear without a GitHub deployment.

  1. Confirm the CMS/code save completed when changing repository content.
  2. Refresh the affected public page.
  3. Check important edits at desktop and phone widths.
  4. Test new external links.
  5. For events, verify detail and RSVP behavior.
  6. For projects, verify gallery and member association.
  7. For payments, verify each destination.
  8. For curated designs, verify Remix reconstructs the saved design code.
  9. For Live Community, publish from an incognito/private browser and verify like/remix/report/self-remove behavior.
  10. For Design Studio changes, also test My Sketchbook, PNG/poster export, and presentation modes.

Article 16

Manage editor and service access

  • Only current maintainers should have GitHub/Pages CMS editing access.
  • Add replacement editors before removing outgoing people.
  • Keep at least two current people capable of administering long-term ownership.
  • Never share one GitHub password among the chapter.
  • If Live Community is enabled, also keep at least two chapter-controlled administrators on the Supabase project.

Article 17

Transfer the website to future chapter leadership

The website should be transferred, not rebuilt.

  1. Transfer the existing GitHub repository to the chapter-controlled organization/owner.
  2. Verify GitHub Pages and Pages CMS under the new owner.
  3. Verify public URL/custom domain and all major CMS sections.
  4. If Live Community is enabled, transfer/invite new chapter administrators to the Supabase project as well.
  5. Do not rotate the public Supabase project URL/publishable key unless the Supabase project itself changes.
  6. Test a live publish, like, remix, report, and owner delete from a normal browser.
  7. Test at least one stored curated showcase code.
  8. Remove previous/test-account access only after both GitHub and Supabase ownership are confirmed.
No website rebuild is required. Repository content and curated design codes transfer with GitHub; the optional Supabase project is simply handed to the next administrators.

Article 18

Troubleshooting common problems

A saved CMS change is not visible

Confirm the CMS save completed and check GitHub Pages deployment status.

A member/project relationship is missing

Confirm the project's Member profile URL name exactly matches the member's Member URL name.

An RSVP/payment button is missing

Check the visibility toggle and required full https:// URL.

A Design Studio share link says invalid

Create a fresh link/code. Do not manually shorten or edit encoded design codes.

Live Community is not visible

Check data/community-backend.json. If disabled, the community code intentionally does not load. If enabled, verify the project URL/publishable key, Anonymous Sign-Ins, Data API grants, RLS setup, and database mode. The static/curated game remains usable while the backend is down.

Publishing returns a permission error

Re-run/compare the SQL setup and confirm RLS policies and table grants exist. Never solve a browser permission error by pasting a secret/service-role key into the site.

A student's “Remove mine” option disappeared

Live ownership uses Supabase anonymous auth stored by the browser. Clearing site storage or changing browsers/devices can lose that anonymous identity. A chapter administrator can still remove the row in Supabase.

A local draft/favorite/sketchbook version disappeared

Those features use local browser storage. Clearing site data or switching browsers/devices can remove them. Share links and exported images are the portable options.

A poster/PNG does not match the canvas

Try the export again after the canvas is fully rendered. Sun Study shadows are serialized for export, while selection handles are intentionally omitted.

Pages CMS shows a React/config error

Hard-refresh Pages CMS first. If it continues, have a maintainer inspect .pages.yml.

Article 19

Privacy, permissions, moderation, and content safety

The GitHub repository is public. Treat repository content as public even when a field is not currently rendered. Live Community adds public user-generated title/credit/caption data stored in Supabase.

  • Never store passwords, secret/service-role API keys, recovery codes, banking credentials, or card information in the repository.
  • Never publish grades, student records, private critiques, or other protected educational data.
  • Get permission before publishing portraits, biographies, public emails, project work, or another person's name.
  • Do not publish copyrighted photography, confidential client work, or third-party material without permission.
  • Periodically review Live Community reports when auto-publish mode is enabled.
  • Use moderated mode instead of auto mode if the chapter does not want user-generated content to appear immediately.
  • Verify payment, RSVP, job, portfolio, social, and other external links.
When uncertain, leave it out and confirm first. Removing public content later does not guarantee it was never copied, cached, or shared.
